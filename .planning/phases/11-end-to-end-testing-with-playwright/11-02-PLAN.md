  <action>
    **1. Create `frontend/tests/e2e/auth.spec.ts`:**

    This spec tests authentication WITHOUT relying on storageState (it tests the auth flow itself). Use `test.use({ storageState: { cookies: [], origins: [] } })` to override the default project storageState and start with a clean browser context.

    Import `LoginPage` from `../pages/login.page`. Tests:

    **test('register new account and redirect to audit'):**
    - Instantiate LoginPage, goto login
    - Call `register()` with unique email (`e2e-auth-${Date.now()}@test.com`) and `MyPassword123@`
    - Assert redirect to /audit using `expectRedirectToAudit()`

    **test('login with existing account redirects to audit'):**
    - Register user via API first (`page.request.post` to `/api/v1/auth/register`)
    - Instantiate LoginPage, goto login
    - Call `login()` with same credentials
    - Assert redirect to /audit

    **test('invalid credentials show error message'):**
    - Instantiate LoginPage, goto login
    - Call `login()` with non-existent email and wrong password
    - Assert errorMessage is visible with appropriate text (e.g., "Invalid" or "incorrect")

    **test('unauthenticated user is redirected to login'):**
    - Clear all cookies: `page.context().clearCookies()`
    - Navigate to `/audit` (protected page)
    - Assert URL contains `/login`

    **2. Create `frontend/tests/e2e/navigation.spec.ts`:**

    This spec uses default storageState (authenticated). Import test helpers for mocking API calls (each page makes API calls on load).

    **test('sidebar shows all navigation links'):**
    - Setup mocks (setupDashboardMocks to prevent API errors)
    - Navigate to `/dashboard`
    - Assert sidebar contains links: Audit, Dashboard, Recommendations, Competitors, Brands
    - Each link has correct href attribute

    **test('navigation links route to correct pages'):**
    - Setup comprehensive mocks (auth + audit list + dashboard + recommendations + competitors + brands)
    - Navigate to `/dashboard`
    - Click each sidebar link in sequence and verify URL changes:
      - Audit -> /audit
      - Dashboard -> /dashboard
      - Recommendations -> /recommendations
      - Competitors -> /competitors
      - Brands -> /brands
    - Use `await page.waitForURL()` between navigations

    **test('auth guard redirects on all protected pages'):**
    - Use `test.use({ storageState: { cookies: [], origins: [] } })` to clear auth
    - For each protected route (/audit, /dashboard, /recommendations, /competitors, /brands): navigate and assert redirect to /login

    **3. Delete or rename `frontend/tests/e2e/auth-and-audit.spec.ts`:**
    - Rename to `auth-and-audit.spec.ts.bak` or delete it entirely. Its 3 tests are now covered by auth.spec.ts (register, login, auth guard) with better structure (POM, no inline waits).

    **Anti-patterns to avoid:**
    - No `waitForTimeout` -- use `expect(locator).toBeVisible()` or `page.waitForURL()`
    - No hardcoded `BASE_URL` -- rely on `baseURL` from playwright.config.ts (use relative paths in goto)
    - No inline mock data -- import from fixtures

  <action>
    **Create `frontend/tests/e2e/audit-lifecycle.spec.ts`:**

    Import `AuditPage` from pages, import `setupAuditPageMocks` and related helpers from fixtures. All tests use mocked API responses (the real pipeline requires Celery + Redis + AI API keys).

    **Mock strategy for audit lifecycle:** Mock the audit API to simulate the polling lifecycle:
    - POST `/api/v1/audit/analyze` returns `{ id: MOCK_AUDIT_ID, status: 'pending' }`
    - GET `/api/v1/audit/${MOCK_AUDIT_ID}` returns evolving statuses:
      - First call: `{ status: 'crawling' }`
      - Second call: `{ status: 'generating_queries' }`
      - Third call: `{ status: 'dispatching' }`
      - Fourth call: `{ status: 'completed', visibility_score: 83, optimization_score: 61, ... }`
    - Use a counter variable in the route handler to cycle through statuses

    **Tests:**

    **test('audit page shows URL input and start button'):**
    - Instantiate AuditPage, goto
    - Assert heading, urlInput, startButton are visible
    - Assert startButton text is 'Start AI Audit'

    **test('starting audit shows progress indicator'):**
    - Setup audit mocks with status progression
    - Instantiate AuditPage, goto
    - Fill URL input with 'https://stripe.com'
    - Click start button
    - Assert progress indicator becomes visible (use `expect().toBeVisible({ timeout: 10000 })`)

    **test('completed audit shows visibility and optimization scores'):**
    - Setup audit mocks that return completed status immediately
    - Mock the audit detail endpoint to return full results (scores, queries, mentions)
    - Instantiate AuditPage, goto
    - Mock audit list to show a completed audit
    - Navigate to audit page where completed audit is displayed
    - Assert visibilityScore and optimizationScore are visible with correct values

    **test('audit results show query list with mention indicators'):**
    - Setup mocks with completed audit including queries with mentions
    - Mock data: 3 queries, 2 with mentions (check marks), 1 without
    - Navigate to audit results
    - Assert query list items are visible
    - Assert mention indicators (check/x icons or text) are present

    **test('empty state when no audits exist'):**
    - Setup mocks with empty audit list
    - Instantiate AuditPage, goto
    - Assert URL input form is visible (ready for first audit)

    **test('audit page with existing completed audit shows results'):**
    - Setup mocks with one completed audit in the list
    - Navigate to audit page
    - Assert results section is rendered with score cards

    **Mock data shapes** -- use the centralized mock data from `mock-data.ts`. Add any additional audit-specific mock data there (MOCK_AUDIT_DETAIL, MOCK_AUDIT_QUERIES, MOCK_AUDIT_MENTIONS) if not already present. If new mock data constants are needed, add them to `mock-data.ts` first.

    **Anti-patterns to avoid:**
    - No `waitForTimeout` for polling simulation -- use counter-based route handlers that return progressive statuses
    - No `networkidle` waits -- use `waitForResponse` for specific API calls
    - No testing of the real Celery pipeline -- all mocked
